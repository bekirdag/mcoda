# Prospective scoring protocol

52 original requests:20 quantitative,10 Python implementation,10 design,10 primary-source research,2 complete web apps. They were authored after repair development. No candidate has received them before the prospective run. Novel requests are not a claim that underlying facts/algorithms are absent from model pretraining.

Three arms: frozen build68 Codali (before), repaired candidate (after), raw same Qwen with tools from repaired candidate. Same model alias, load-balancing pool, output/context configuration and effort budgets. Rotate order. Single attempt per arm per case; retain infrastructure failures and all costs, never silently retry uncertain outcomes. Shared dependencies/OS and backend load are limitations. Docdex server-owned inference is outside client token accounting.

Questions are100 points each. Quantitative cases have5 fields worth20 each with relative1e-5/absolute1e-7 numeric tolerance and exact structural comparison otherwise. Invalid/non-JSON answers score0; extra/missing keys cap score90, in addition to lost missing fields. Code has5 independently authored executable test criteria worth20 each, run against only the final delivered Python module in an offline sandbox. Required single fenced module format violations cap90. Inspect source for grader interference, unsafe side effects and untested requirement gaps; reject tampering. Reference implementation passed all50 test criteria before the run. Test success is limited evidence, not proof of universal correctness.

Design/research each have5 predeclared criteria scored0,10,20 for absent/wrong, partial, complete. The primary Codex evaluator uses delivered content and actual receipts, not candidate self-grades or another Qwen-only judge. Retrieval is not truth; a source must support the exact claim and version/scope. Mark source gaps, unsupported section citations, excessive copying, fabricated checks and contradictions. A correct conclusion may earn semantic points while losing evidence points. Report author/evaluator overlap and single-review uncertainty; no claim of fully blinded independent replication.

App score: delivery20, domain API40, security/privacy20, rendered UI15, source/delivery honesty5. Delivery API checks exclude installation itself from denominator (it is prerequisite telemetry); remaining delivery group checks share20. Domain/security check pass fractions scale40/20 respectively. Failed prerequisites do not remove downstream checks. UI is assessed with actual browser user journeys, screenshots, mobile360px and keyboard/error behavior; unusable/nonexistent UI earns0. Source/honesty five points require inspectable maintainable delivered source and truthful evidence; note substantive security/business defects not covered by checks, adjust affected criterion with written reasons consistently across arms. Do not repair submitted projects. All evaluation changes take place in independent copies under isolated processes, leaving originals untouched.

Report all52 and question/app/category breakdowns. Also show matched-delivered comparisons where appropriate, without removing failures from the primary average. Token/time ratios use summed client usage and execution elapsed times; service waiting recorded separately. Disclose confidence limitations and whether the10% intelligence / <=1.5x token/time targets are met, rather than selecting favorable subsets.

External service limitation at freeze: configured SearXNG reports many suspended/rate-limited engines and weak discovery; direct official browser access works. Research requests give starting primary URLs equally to all arms. Any service changes during run must be recorded and cannot silently alter frozen runtime/configuration.
